# Docker and Omeka S audit — 8 September 2026

## Outcome and scope

Keep the existing Compose architecture. Targeted fixes improve update reliability,
backup handling and security without introducing another orchestrator, database,
monitoring service or mandatory institution-specific dependency.

The review covers the Dockerfile, base and deployment Compose files, nginx,
PHP-FPM settings, operation scripts, extension manifests and GitHub workflows.
All repository documentation and operator messages are in English. AMIRA remains
an optional worked example under `deploy/amira/` and its Compose overlay.

Changes are local and have not been deployed or merged. This checkout has no
`.env`, no reachable local Docker engine and no supplied deployment SSH access.
Production logs, actual volumes, workload peaks, firewall rules and TLS have not
been inspected. No production database migration or restore was performed.

## Implemented improvements

| Area | Problem | Result |
|---|---|---|
| PHP cache | Timestamp checks were disabled despite extensions being mutable | OPcache checks modified files every two seconds; obsolete `fast_shutdown` removed |
| Browser cache | Stable URLs were declared immutable for a year | Static resources use conditional revalidation with ETag/Last-Modified |
| PHP source exposure | Only lowercase `.php` suffixes were blocked | Case-insensitive PHP/PHTML/PHAR and path-suffix protection, while exact `/index.php` remains the front controller |
| Proxy trust | Every private LAN was trusted; forwarded HTTPS was unconditional | One configurable proxy CIDR and HTTPS forwarding only from a trusted peer |
| Database durability | Recent commits could be lost on host failure | Redo is flushed on commit; storage must still honor flush requests |
| Database readiness | Backup/restore could connect to MySQL's temporary initialization socket | Authenticated TCP query against the configured database before proceeding |
| Volume portability | Helpers guessed `<project>_<volume>` names | Resolve actual mounted volume names, including custom names, from Compose |
| Inactive extensions | Old volumes and other deployments could be selected | Back up mounted extension volumes only; update only active deployment manifests |
| Backup paths | Relative paths could be interpreted as Docker volume names | Resolve an absolute host path before mounting |
| Backup completeness | Interrupted backups could resemble old unchecked archives | Refuse non-empty destinations; retain `BACKUP_INCOMPLETE` on failure; reject incomplete restores |
| Consistent media backup | SQL and files were copied while writers remained active | Optional `--quiesce` stops application services and restarts them on exit, including error paths |
| Search backup | A live Typesense tar was presented as a usable backup | New backups omit the regenerable index; legacy archive restoration requires explicit `--restore-search` |
| Restore cancellation | Existing configuration could change before confirmation | Replace Omeka configuration only after confirmation and service shutdown |
| Retention | The documented `find` could select the backup parent directory | Restrict deletion to dated child directories |
| Extension migrations | Image-managed extensions exited before migrations | Apply pending module migrations in both layouts; inventory failures stop the script |
| Theme updates | Already-correct target names failed and temporary copies blocked repeat runs | Accept existing target directories and remove the old copy after successful replacement |
| Secret handling | Restored deployment configuration could enter a build context | Exclude restored/migrated config files; ignore `.env.*` except the example |
| Resource sizing | A comment incorrectly claimed five 512M workers fit within 1536M | Correct the guidance; expose container CPU/memory limits as settings without changing defaults |
| FPM configuration | Invalid relationships between pool sizes were found only by PHP-FPM | Validate `min_spare <= start <= max_spare <= max_children` before startup |
| Diagnostics | No compact generic health summary | Read-only `scripts/health-report.sh`, including health, restarts, OOM flag and resource use, without environments or logs |
| CI | A multi-argument `bash -n` checked only the first script | Check each script; add operation regression tests and extend HTTP probes |
| Test isolation | Refusing a smoke run could still trigger deletion of existing configuration in its cleanup trap | Refuse occupied checkouts before registering cleanup |
| Fork portability | Dependabot assigned a named upstream operator | Remove personal assignments; AMIRA release checking requires upstream ownership or explicit fork opt-in |

Old responses already cached by a browser can remain fresh under their old
one-year policy. A forced reload or changed asset URL may be needed once.
The new policy governs responses fetched after deployment. Nginx's file cache
can still delay observing a replacement for its configured validation interval.

## Existing protections retained

PHP runs as `www-data`, drops all Linux capabilities and uses a read-only root
filesystem. Database credentials are generated in protected tmpfs storage.
Sessions have persistent storage. Database and search ports are not published;
web binds to loopback by default. Source, configuration and dependency paths are
blocked by nginx. Docker logs rotate. Images and CI actions are digest/commit
pinned. The optional immutable overlay keeps extension code in images.

AMIRA's MCP service remains isolated from the database network, and its absence
does not prevent the website from starting. It is not enabled in the base stack.

## Validation and remaining deployment work

Local checks include the four supported Compose combinations, a custom resource
profile, Bash syntax, ShellCheck and 16 regression tests with a simulated Docker
CLI. A standalone
Windows nginx 1.30.4 test also exercises the actual nginx configuration with
fixture files and an intentionally unavailable FastCGI upstream. Its 24 HTTP
checks include trusted and untrusted forwarded-IP/HTTPS scenarios. The Linux
image build, Docker entrypoint rendering and a real restore still require a
working Docker engine; standalone tests do not replace them.

Before applying changes to a live installation:

1. Run the CI smoke suite in an independent Linux checkout with disposable data.
2. Review [institution setup](INSTITUTION_SETUP.md), especially proxy trust,
   resource limits and custom volume requirements.
3. Take a backup. Use `--quiesce` for a maintenance window when SQL/media
   consistency matters, and pause any external writers as well.
4. Rebuild matching PHP and web images with `bash scripts/rebuild-code.sh --pull`.
5. Apply the database command change with `docker compose up -d db` during the
   maintenance window; the application rebuild helper does not necessarily
   recreate an already-running database.
6. Run `bash scripts/health-report.sh`. Check public/admin pages, a media upload,
   thumbnails, background jobs and search. Measure memory during imports.
7. Verify off-host backups through an independent restoration, TLS renewal and
   the actual externally exposed ports.

Never run `docker compose down -v` against production data. An unhealthy
container is not automatically restarted by Docker's restart policy. The
health report can be integrated with an institution's existing monitoring; it
does not install a scheduler or notification service.

Five simultaneous 512M PHP requests can exceed the default 1536M container cap
before caches, tmpfs and background jobs are counted. Tune from measurements;
do not raise workers blindly. FPM's `OOMKilled` flag alone cannot detect every
worker-level OOM event, so also inspect host/kernel logs when diagnosing failures.

Database/file snapshots are not atomic unless all relevant writers are stopped.
Extension replacement and migrations are not transactional. Some upstream
extension references remain floating by design; pinned images alone do not make
all rebuilds reproducible. Use reviewed release archives in your own manifests
when reproducibility is required. The media marker detects uninitialized storage,
not a cryptographically unique association between database and media.

The optional AMIRA visualization volume still masks shipped module data after
its initial population. Follow that module's release instructions before
replacing generated data; no real visualization volume was removed in this audit.
