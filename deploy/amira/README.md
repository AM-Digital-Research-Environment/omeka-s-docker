# AMIRA deployment overlay

This directory holds everything specific to the DRE production deployment at
[data.africamultiple.uni-bayreuth.de](https://data.africamultiple.uni-bayreuth.de) — the
[Africa Multiple](https://www.africamultiple.uni-bayreuth.de/) research-data platform (AMIRA).
The base stack in the repository root stays a generic, reusable Omeka S template; the overlay
adds the AMIRA pieces on top without forking anything.

It also doubles as the worked example of how to extend the template with your own
deployment-specific services — copy the pattern, not the content.

## What the overlay adds

| Piece | Defined in | How it attaches |
|-------|-----------|-----------------|
| `amira-mcp` service | [`compose.amira.yml`](../../compose.amira.yml) | An extra service on its own private `mcp` network, shared only with `web` |
| `/mcp` web address | [`nginx-mcp-location.conf`](nginx-mcp-location.conf) | Mounted into `/etc/nginx/templates/extra-locations/`, which the base `nginx.conf` includes automatically |
| `/favicon.ico` | [`nginx-favicon-location.conf`](nginx-favicon-location.conf) | Same extension point; serves DRE-theme's `favicon-48.png` at the domain root |
| `/.well-known/void` | [`nginx-well-known-void-location.conf`](nginx-well-known-void-location.conf) | Same extension point; exempts this one path from the dot-path deny so DRE-LinkedData can answer it |
| DRE modules | [`modules.txt`](modules.txt) | Installed into the image via the `EXTRA_MODULES_FILE` setting |
| DRE-theme | [`themes.txt`](themes.txt) | Installed via `EXTRA_THEMES_FILE`, renamed to the folder the site rows expect |
| `dre` vocabulary | [`vocabularies/`](vocabularies/) | `dre.rdf` + `dre.json` mounted into the vocabulary folder; imported on first start. Namespace `https://data.africamultiple.uni-bayreuth.de/ontology/dre#` |
| `/ontology/dre` | [`nginx-dre-vocabulary-location.conf`](nginx-dre-vocabulary-location.conf), [`nginx-dre-vocabulary-map.conf`](nginx-dre-vocabulary-map.conf) | Serves the `dre` vocabulary as HTML, Turtle, RDF/XML or JSON-LD by `Accept`; the files are generated by [`vocabularies/build_dre_vocabulary.py`](vocabularies/build_dre_vocabulary.py) |
| Search | base `docker-compose.yml` | Switched on with `COMPOSE_PROFILES=search`, used by the DRESearch module |
| `/sparql` (optional) | [`sparql/`](sparql/), [`nginx-sparql-location.conf`](nginx-sparql-location.conf), [`nginx-sparql-limits.conf`](nginx-sparql-limits.conf) | A read-only SPARQL endpoint over the DRE-LinkedData dump, switched on with the `sparql` profile — see [below](#sparql-endpoint) |
| Storage for precomputed visualizations | [`compose.amira.yml`](../../compose.amira.yml) | A `dre_visualizations_private` volume — see [below](#the-visualizations-volume) |
| iframe embedding | `.env` | `FRAME_ANCESTORS` permits the frederickmadore.com domains |
| MCP version | `.env` | `AMIRA_MCP_VERSION`; leave unset to use the release pinned in [`compose.amira.yml`](../../compose.amira.yml) |

The modules installed for AMIRA are DRESearch, DRE-SEO, DRE-Visualizations
(which provides the `DreVisualizations` module), DRE-LinkedData (which provides
the `DRELinkedData` module), BulkEdit, Reference, and LocalContexts. [`modules.txt`](modules.txt) is the authoritative list and
explains why each one is pinned the way it is.

Every DRE module and DRE-theme is installed from its published release archive,
so the images carry the packaged module or theme rather than a clone of its
development tree. `bash scripts/update-extensions.sh` moves those pins to the
newest release and updates the running site's copies in place, without
rebuilding the images (add `--rebuild` to also rebuild them).

## Activating the overlay

One-time edit of the server's `.env`:

```bash
COMPOSE_FILE=docker-compose.yml:compose.amira.yml
COMPOSE_PROFILES=search
FRAME_ANCESTORS="'self' https://www.frederickmadore.com https://slides.frederickmadore.com"
TYPESENSE_API_KEY=<long random string>
SERVER_NAME=data.africamultiple.uni-bayreuth.de
```

Add `sparql` to `COMPOSE_PROFILES` (`COMPOSE_PROFILES=search,sparql`) to run
the [SPARQL endpoint](#sparql-endpoint) as well.

`AMIRA_MCP_VERSION` is deliberately absent: leaving it unset takes the release
pinned in [`compose.amira.yml`](../../compose.amira.yml), and
[`update-amira-mcp.sh`](update-amira-mcp.sh) writes it into `.env` when you move
to a newer release.

Docker Compose reads `COMPOSE_FILE` and `COMPOSE_PROFILES` from `.env`, so every
`docker compose` command (`up`, `logs`, `ps`, the backup scripts, …) automatically includes
the overlay — no `-f` flags needed. Plain `docker compose up -d` runs the full AMIRA stack;
a checkout without these `.env` lines runs the generic template.

After changing `.env`, apply it:

```bash
bash scripts/rebuild-code.sh
```

Use this rather than `docker compose up -d --build` — it rebuilds the PHP and web
images together (the automated checks reject them being out of step) and waits
until both report healthy before returning.

## MCP server (AMIRA)

The overlay runs the [amira-mcp-server](https://github.com/AM-Digital-Research-Environment/amira-mcp-server),
exposing this instance's public, read-only dataset to AI assistants over the
[Model Context Protocol](https://modelcontextprotocol.io/) (Streamable-HTTP/SSE) at:

```
https://data.africamultiple.uni-bayreuth.de/mcp
```

Point any MCP client (Claude, etc.) at that URL as a Streamable-HTTP server to get
search/list/get tools over the collection. The server bundles a snapshot of the public
Omeka S API and refreshes it periodically (`AMIRA_LIVE_REFRESH=true`), so it adds no load
to the live database.

### How requests are routed

`/mcp` must bypass Omeka's front controller, or Omeka would appropriate the URL
(404/redirect). The `web` nginx handles this with a dedicated, higher-precedence location
(`location ^~ /mcp` in [`nginx-mcp-location.conf`](nginx-mcp-location.conf)) that proxies to
the `amira-mcp` container with SSE buffering disabled. A host-level TLS reverse proxy in
front of the stack forwards `/mcp` through unchanged; for true un-buffered streaming and
per-client rate-limiting at that layer, see the optional tweaks in
[`MCP_HOST_NGINX.md`](MCP_HOST_NGINX.md).

### Keeping it up to date

The service builds from a published upstream release tag. Preview or deploy the
latest stable release with:

```bash
bash deploy/amira/update-amira-mcp.sh latest --dry-run
bash deploy/amira/update-amira-mcp.sh latest
```

The helper validates the published tag, records it in `.env`, builds it, and
recreates only `amira-mcp`. Use `--refresh-data` for a same-version rebuild of
the bundled data snapshot. The rest of the stack keeps running.

### Security

Like the search engine, the MCP server is set up so that adding it doesn't make
the site easier to attack:

- **Never exposed directly.** It opens **no ports** — it sits on a private `mcp`
  network shared only with the web server, and the outside world reaches it solely through
  the hardened `web` nginx at `/mcp`. It cannot reach the database or the search index at
  all.
- **Read-only and public by design.** The underlying data is the same public collection
  already served by the site, so the endpoint needs no credentials. Abuse is bounded by the
  server's own per-visitor rate limit (`AMIRA_RATE_LIMIT`, 120 requests/minute by default),
  plus the optional coarser limit at the host nginx in
  [`MCP_HOST_NGINX.md`](MCP_HOST_NGINX.md). The per-visitor part needs
  `AMIRA_TRUST_PROXY=true` — set in [`compose.amira.yml`](../../compose.amira.yml) — because
  every request reaches the server from the web container, so without it all visitors would
  share one bucket and a single busy client could lock out everyone else. That setting makes
  the server take the client address from `X-Forwarded-For`, so that header becomes the
  rate-limit key — which is why [`nginx-mcp-location.conf`](nginx-mcp-location.conf)
  *overwrites* it with the single address this stack resolved itself rather than appending
  to the caller's chain. Appending would let a caller forge a fresh IP per request and skip
  the limit altogether. Sending one entry is also robust to upstream changing which end of
  the chain it counts from (leftmost in v1.17.0, `AMIRA_PROXY_HOPS` from the right in
  v1.19.0). CI asserts the pair stays consistent.
- **Locked down like everything else:** no special privileges, a read-only filesystem, and a
  cap of a quarter CPU and 256 MB so it can't crowd out the site.
- **Nothing to back up.** Its copy of the data is rebuilt from the public API, so it keeps
  no state of its own.
- **The site never waits on it.** The `/mcp` rule looks the server up at the moment a request
  arrives, so if `amira-mcp` is stopped, crashed, or still building, only `/mcp` returns an
  error — the rest of the site is unaffected.

## SPARQL endpoint

DRE-LinkedData publishes the whole public graph as a gzipped N-Triples dump at
`/linked-data/dump.nt.gz`. The optional `sparql` service loads that dump into
[Oxigraph](https://github.com/oxigraph/oxigraph) and answers SPARQL 1.1 queries
at:

```
https://data.africamultiple.uni-bayreuth.de/sparql
```

Send a query as `GET /sparql?query=...` or `POST` it, as
`application/sparql-query` or as a form. Without a query, `GET /sparql` returns
the service description, with the endpoint's public `https://` address put back
by nginx (Oxigraph, reached over plain HTTP, would state `http://`). A browser
opening `/sparql` itself is sent to the *Linked open data* page
(`/s/amira/page/linked-open-data`), which explains the endpoint and runs
example queries. Cross-origin requests are allowed, so browser tools such as
YASGUI can use the endpoint directly. Results are sent uncompressed:
compressing them would take the web server's small CPU share, which every page
request depends on. Writes are refused, and `SERVICE` (federated queries) always
fails: the service has no network (see below).

### Switching it on

It is off unless the `sparql` profile is active:

1. Make sure the DRELinkedData module has generated a dump (**Modules > DRE
   Linked Data > Configure > Generate the dump now**).
2. Add the profile in `.env`: `COMPOSE_PROFILES=search,sparql`.
3. Start it with `docker compose up -d --build sparql`, then recreate `web`
   once so it picks up the new locations: `docker compose up -d web`.
4. In the module's configuration, set **SPARQL endpoint** to
   `https://data.africamultiple.uni-bayreuth.de/sparql`. The VoID description
   then advertises it as `void:sparqlEndpoint`, and the Linked open data page
   block links to it. Leave the field empty and nothing is advertised.

To switch it off, take `sparql` out of `COMPOSE_PROFILES`, run
`docker compose stop sparql`, and empty the module setting. `/sparql` then
answers `503`, and the rest of the site is unaffected either way.

### Keeping it current

The endpoint follows the dump, so it is as current as the last dump. Once a minute the service reads
`files/dre-linked-data/state.json`. When the module has published a new dump, it
loads that dump into a fresh store while the old one keeps answering, and swaps
it in only once the load has finished, so a query never sees half a graph. At
about 220,000 triples a load takes two seconds. Queries running at the moment
of the swap are cut off.

A store is never edited in place: if a load fails, the previous one stays in
service and the next check tries again. A restart reuses the last completed
store, so it does not reload. The `sparql_data` volume holding the stores is not
backed up; a fresh one is rebuilt from the dump on start. Each new store is
compacted (`oxigraph optimize`) before it is swapped in.

What does need scheduling is the dump itself, which the module writes only when
asked. Its command-line script with `--if-stale` writes one only when records
changed since the last, so it is cheap to run nightly, after the sync:

```cron
# /etc/cron.d/amira-linked-data  (replace <user> and the path)
30 4 * * * <user> cd /path/to/omeka-s-docker && docker compose exec -T -u www-data php php modules/DRELinkedData/scripts/generate-dump.php --if-stale --quiet
```

It exits `0` when it wrote a dump or found nothing to do, and the endpoint picks
the new dump up within a minute.

### What keeps it from slowing the site down

- **Its own budget.** The container is capped at half a CPU and 256 MB and has a
  quarter of the default CPU weight, so whenever it competes with PHP, MySQL or
  nginx for the processor, those win. It idles under 10 MB.
- **Query timeout, with a backstop.** A query is cancelled after
  `SPARQL_QUERY_TIMEOUT` (30 s). Oxigraph checks that deadline only when it
  reads from the store, so a query that multiplies results already in memory
  can outlive it. A watchdog in the entrypoint therefore restarts the server if
  it stays saturated for twice the timeout. The restart takes well under a
  second and reuses the store. Tested on this host: a deliberate cross product
  was stopped at 60 s, and Omeka's pages kept answering in under 0.1 s
  throughout.
- **A limit on the whole request.** Both timeouts above apply to each read and
  write, so a result that keeps streaming, or a client that reads it slowly,
  outlives them. Each connection is therefore relayed under `timeout` and
  closed after `SPARQL_REQUEST_LIMIT` (60 s), whatever it is doing; the client
  sees a truncated response. Without it a three-way join over the whole graph
  streamed 399 MB for 42 s, holding one of the four slots.
- **Limits at nginx.** Each visitor gets 60 queries a minute (bursts of 20) and
  two at a time, and the endpoint as a whole runs at most four at a time. Past
  that, clients get `429`. Query bodies are capped at 64 KB, and large results
  are streamed to the client rather than spooled into the tmpfs that PHP
  responses also buffer through.
- **No network at all.** SPARQL's `SERVICE` keyword makes the server fetch
  other URLs, and Oxigraph has no switch to turn it off. On any Docker network,
  even an internal one, a public query could aim it at Omeka or at the host's
  own ports. So the service runs with `network_mode: none` and nginx reaches it
  through a Unix socket on the `sparql_socket` volume. `SERVICE` fails
  immediately, and CI asserts this isolation stays in place.
- **Read-only throughout.** The server opens its store read-only, reads the
  media volume read-only, runs as an unprivileged user on a read-only
  filesystem, and only its `/sparql` path is exposed.

The result size is bounded by the graph and the request limit. Constructing
every triple returns about 35 MB of N-Triples in roughly four seconds, the same
data the dump already offers in compressed form.

### Updating

The Oxigraph and Debian base images are pinned by digest in
[`sparql/Dockerfile`](sparql/Dockerfile), and Dependabot proposes updates. To
apply one: `docker compose build sparql && docker compose up -d sparql`.

## The visualizations volume

The DreVisualizations module precomputes its dashboards, knowledge graph, and
photo galleries. Since v2.29.0 it writes them to private storage outside the
document root, named by `DRE_VISUALIZATIONS_DATA_DIR`, and serves them through
an Omeka endpoint rather than as static files. The overlay points that setting
at its own volume, `dre_visualizations_private`, mounted for `php` only; nginx
has nothing to read from it.

It earns its keep two ways: the output survives restarts and cannot be swept up
by a temporary-directory cleanup, and roughly a gigabyte of regenerable output
stays out of every backup.

**It is not backed up, on purpose.** Everything in it can be regenerated from the
database with the admin "Regenerate" action. Disaster recovery is: restore the
database and media, start the stack, regenerate.

The module's own shipped files (its static geography under `asset/`) are no
longer covered by this volume. They are ordinary module content on the module
storage, so updating the module updates them; no volume needs deleting.

## Rolling your own overlay

To adapt this pattern for another deployment:

1. Create `deploy/<name>/` and put your own module list, theme list, service
   configuration, and vocabularies in it.
2. Write a `compose.<name>.yml` in the repository root that adds your services
   and connects your files:
   - extra web addresses → mount a `.conf.template` into
     `/etc/nginx/templates/extra-locations/`
   - your modules → `build.args.EXTRA_MODULES_FILE: deploy/<name>/modules.txt`
   - your themes → `build.args.EXTRA_THEMES_FILE: deploy/<name>/themes.txt`
   - your vocabularies → mount the `.owl` and `.json` pair into
     `/usr/local/share/omeka-vocabs/`
3. Switch it on with `COMPOSE_FILE=docker-compose.yml:compose.<name>.yml` in
   `.env`.

Two things worth copying from this example:

- Set the same `EXTRA_MODULES_FILE` and `EXTRA_THEMES_FILE` on **both** the `php`
  and `web` services. They share one code layer, and the automated checks will
  fail the build if the two disagree.
- If your extra service needs to be reachable through the site, give it its own
  private network shared only with `web`, as `compose.amira.yml` does with `mcp`.
  It then has no route to the database.

Because you never edit the shared files, you can keep pulling updates from this
template without merge conflicts.
